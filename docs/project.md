### 入力と表示

- モデル選択時に固定候補の既定バージョン・SKU・モデル名と同じデプロイ名を自動設定する。手動変更でき、モデルを選び直すと再設定する。
- 新規名は[Azureの命名規則](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/resource-name-rules)に基づく。Foundryは2〜64文字の半角英数字・ハイフン、先頭末尾は英数字。RGは1〜90文字のUnicode文字・十進数字・アンダースコア・ハイフン・ピリオド・括弧、末尾ピリオド禁止。同一スコープの固定候補との重複は大文字小文字を区別せず拒否する。Azure側の使用可否照会は行わない。
- RG・Foundry名に入力モードurl、自動大文字化・自動訂正・スペルチェック無効を指定する。[入力モード指定](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/inputmode)はOSのIME強制OFFを保証しない。Windowsでの実際の切替は未検証。
- 重複した説明・手順見出しを省き、一覧の追加ボタンは件数と同じ行の右端へ置く。モックの補助操作は入力欄の後ろに置く。
- ダイアログ・候補取得状態・名前の補足／エラー・一覧の取得状態に必要な領域を確保し、非同期状態で既存入力欄を動かさない。フォーカスは内側の枠とし、スクロール境界で切れる外側の太い二重枠を廃止する。ネイティブselectとキーボード操作は維持する。画面規則は[frontend/src/AGENTS.md](../frontend/src/AGENTS.md)。

### F1. アカウント横断のデプロイ一覧と絞り込み

目的: 複数アカウントにデプロイされたモデルのデプロイ名とレート制限の設定値を、一つの一覧で確認・比較可能にする。

<a id="f1-agreement"></a>
#### ヒアリングで合意した要件

判断者: リポジトリ所有者。日付: 2026-09-13。根拠: 本タスクで一問ずつ確認した回答。仮実装の画面・操作を引き継ぐ前提は取り下げ、ゼロから検討する。確認済みの利用状況は、テナントをまたいで普段約10アカウントを利用すること。

| 観点 | 合意内容 |
| --- | --- |
| 対象と初期表示 | アクセス権のある全 Foundry アカウントのデプロイを、テナントをまたいで一つの一覧に表示する。普段使う約10アカウントだけには限定しない。 |
| テナントの権限不足 | 権限不足のテナントは取扱い対象外とし、対象件数・取得エラー・不完全表示に含めず、起動時や更新時に通知しない。対象アカウントの取得時に発生する権限不足は、従来どおり取得エラーとして扱う。 |
| 性能による例外 | 全件表示が重すぎる場合は、既定の表示対象を単一アカウントとすることを許容する。実際の取得時間を確認して判断する。許容時間と既定範囲は未確定（U3）。エラー時に対象を自動縮小する意味ではない。 |
| 主な確認項目 | デプロイ名と設定 TPM（1分あたりのトークン数）を必須の表示項目とし、設定 RPM（1分あたりのリクエスト数）も取得できる場合に表示する。 |
| 絞り込み | テナント、サブスクリプション、リージョン、アカウント、モデル、デプロイ名の6属性を対象にする。 |
| 更新契機 | 起動時に取得し、その後は更新ボタンで手動取得する。定期的な自動更新は行わない。 |
| 取得の進捗 | サブスクリプションごとの対象探索と、アカウントごとのデプロイ取得の完了数を表示する。総数が判明するまでは未確定として示し、推測の割合を出さない。完了したアカウントから成功行と失敗情報を反映し、全件完了を待たずに確認できるようにする。 |
| 部分失敗 | 成功したデプロイを一覧に表示する。エラーがあることと失敗アカウント数（判明時）、一覧が不完全であること、「エラー詳細」ボタンを一覧に表示する。取得に失敗したアカウントや探索対象、コード、理由、対処は別画面に全件表示する。 |

エラー詳細画面への分離合意: 2026-09-13。判断者: リポジトリ所有者。根拠: 本タスクの明示指示。従前の「同一画面の別領域に詳細を表示する」という合意を、今回の指示により変更し、デプロイ一覧には成功行、エラーの概要と失敗アカウント数（判明時）、不完全表示、「エラー詳細」ボタンだけを表示し、失敗アカウントまたは探索対象のコード、理由、対処を詳細画面へ分離する。この変更の合意と、変更後のモック動作確認および利用者の動作合意は区別する。

列配置の合意: 2026-09-13。判断者: リポジトリ所有者。根拠: 本タスクの明示指示。概念的上位を左から配置することを基本とし、列は左からテナント、サブスクリプション、リージョン、アカウント、モデル（バージョンを併記）、デプロイ名、SKU、設定 TPM、設定 RPM の順とする。この時点の合意対象は列順。

絞り込みの合意: 2026-09-13。判断者: リポジトリ所有者。根拠: 本タスクの「OKですが、いずれかの項目で絞り込んだら、他のプルダウンの項目は選択可能な物だけだしてください」という回答。5属性は選択式、デプロイ名は部分一致検索とし、各プルダウンには他の絞り込み条件に合うデプロイで選択可能な候補だけを出す。変更後モックの動作合意は本節末尾に記録する。

一覧の行はデプロイ単位、取得エラーはアカウント単位で扱う。異なるアカウントに同名デプロイが存在しても区別できるよう、各行に所属テナント・サブスクリプション・アカウントとリソース識別子を保持する。TPM を SKU の Capacity で代用しない。数量欠損の表示はモックで確認・合意済み。各モデル・SKUで設定値を正しく取得できるかは実接続で検証する（U3）。

テナントの権限不足に関する変更合意: 2026-09-13。判断者: リポジトリ所有者。根拠: テナントの権限は簡単に追加できず、毎回表示されるのは好ましくないため、取扱い対象外とするという本タスクの明示指示。テナント権限不足を探索失敗として通知する従前の扱いを変更し、対応するモック状態を廃止する。未ログイン、Azure CLI未導入、対象アカウントの権限不足や通信障害の扱いは維持する。

認証は [Azure CLI credential](https://learn.microsoft.com/en-us/azure/developer/go/sdk/authentication/azure-cli) に委譲し、アプリからログインや `az account set` を実行しません。各 ARM クライアントの URL にはサブスクリプション ID を渡し、資格情報にはそのサブスクリプション ID を指定します。現行の Azure CLI は `tenant` と `subscription` の同時指定を受け付けないため、サブスクリプション ID（テナントを一意に特定する値）を使います。Azure CLI の `--all` に含まれる `id == tenantId` のテナントレベル擬似エントリは ARM サブスクリプションではないため対象外にします。SDK の RP 自動登録は無効化し、F1 は読取だけを行います。

Windows版Azure CLIの標準出力・標準エラーは、[CLI境界](../internal/azurego/cli_windows.go)でWindowsの既定ANSIコードページからUTF-8へ変換してから使用します。2026-09-13、この環境のMSI版ランチャーはPythonを`-I`（隔離モード）で起動し、実際のパイプ出力はCP932でした。[Pythonの標準入出力仕様](https://docs.python.org/3.14/library/sys.html#sys.stdout)に合わせて`GetACP`でコードページを取得し、[MultiByteToWideChar](https://learn.microsoft.com/en-us/windows/win32/api/stringapiset/nf-stringapiset-multibytetowidechar)の`MB_ERR_INVALID_CHARS`で厳密変換します。不正バイトを黙って置換せず、変換失敗を取得エラーにします。文字コードの推測や、`chcp`・OS設定・Azure CLI設定の変更は行いません。既存の`golang.org/x/sys`を直接利用し、新規依存は追加していません。CLIの配布方式やPythonの既定文字コードが変わる場合は、この入出力契約を再検証します。

### レート制限の外部仕様の確認

2026-09-13、Microsoft の [Deployments List（API 2025-06-01）](https://learn.microsoft.com/en-us/rest/api/microsoftfoundry/accountmanagement/deployments/list?view=rest-microsoftfoundry-accountmanagement-2025-06-01) を確認しました。応答には `sku.capacity`、`properties.rateLimits`、`properties.callRateLimit` が定義されていますが、直接 `tpm` / `rpm` という名前の項目はありません。F1 の表示契約では `properties.rateLimits` の `key` が `token` の値を TPM、`request` の値を RPM とし、`count` と `renewalPeriod` から1分あたりへ正規化します。欠損・不正値・1分あたりに整数化できない値は不明のままにします。

[クォータの公式資料](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/quota) は、容量単位と TPM/RPM の対応がモデルにより異なると説明しています。また、[Provisioned の容量](https://learn.microsoft.com/en-us/azure/foundry/openai/concepts/provisioned-throughput) は PTU で扱われます。このため、`sku.capacity` の生値を TPM として表示したり、全モデル・SKU に一律の換算を適用したりしません。実接続では11デプロイを取得し、11件のRPM、10件のTPMを `rateLimits` から表示でき、TPM欠損の1件は不明になりました。Portal の設定値との照合、別モデル・SKUおよびページング境界の網羅性は U3 の残件です。

取得要求の単位: アカウント探索に使う Resources List はサブスクリプション単位、[Deployments List](https://learn.microsoft.com/en-us/rest/api/microsoftfoundry/accountmanagement/deployments/list?view=rest-microsoftfoundry-accountmanagement-2025-06-01) はアカウント単位で、どちらも複数ページになり得ます。このAPI構造を踏まえ、進捗はHTTP要求数ではなく各対象の全ページ取得の完了数で扱います。失敗で終了したアカウントとデプロイ0件の成功も完了数に含めます。探索とデプロイ取得では総作業量が異なるため、全工程を通した推測のパーセントは表示しません。

実Azureの探索進捗では、権限不足で対象外になったサブスクリプションを完了数・総数に含めず、その対象の進捗通知も発行しません。除外対象の判別が終わるまで総数を未確定とし、全探索応答の処理後に対象内の件数を確定します。認証・通信エラーは対象内の失敗として件数と失敗情報に保持します。

### F1 モックの構成と画面

本番用の [DeploymentService](../internal/service/deployments.go)、`GetDeployments`、`GetEnvironment`、[React 画面](../frontend/src/App.tsx)、および [生成した TypeScript 型・呼出し](../frontend/bindings/github.com/nuitsjp/azfoundry-deck/internal/service/deploymentservice.ts) を共用し、Azure 境界の fetch 関数だけを [mock.Provider.Fetch](../internal/mock/provider.go) に置き換えます。[モック専用サービス](../internal/mock/service.go) の `NewMockService(provider).SetScenario` は次回取得の状態だけを設定し、選択しただけでは取得を開始しません。モック専用の状態設定を本番の `DeploymentService` に持ち込みません。

一覧とエラー詳細は同じ取得結果を参照します。一覧から「エラー詳細」で遷移しても取得せず、「デプロイ一覧に戻る」では結果、絞り込み条件、最終取得時刻を保持します。エラー詳細画面の画面名は「エラー詳細」とし、失敗アカウントまたは探索対象、コード、理由、対処を全件表示します。両画面上部のモック状態切替と更新は共通の次回取得状態を設定し、詳細画面で成功更新した場合は「取得エラーはありません」と表示します。

ブラウザーの再読み込み時は、モック専用の `GetScenario` で現在の設定を読み、選択欄と取得結果を一致させます。Windows版とブラウザー版の違いは Wails のビルドタグだけで、どちらも同じ画面、型、生成バインディング、Goサービス、固定データを使います。

Wails serverモードの書き込み制限は、30秒の読込中シナリオを完了まで再現できるよう45秒に設定しています。既定値30秒とモックの待ち時間が同じで、応答を返す前に制限へ達するためです。実Azureの取得タイムアウトを合意したものではありません。

固定データは3テナント、5サブスクリプション、10アカウント、24デプロイです。成功シナリオでは同名デプロイを複数アカウントに置き、各行の `id` と完全なアカウントARMリソースIDで区別します。`tpm` と `rpm` は `*int64` から `number | null` として生成し、欠損は `null` のまま返します。値は SKU の Capacity やモデル別の換算から求めず、画面確認用に独立して設定した架空値です。JSON の `deployments` と `failures` は常に空配列または要素を持つ配列で、`null` にはしません。`failures` は対象範囲内の失敗アカウントまたは探索対象、コード、理由、対処を保持します。対象外のテナント権限不足はfetch境界で除外し、この結果へ含めない契約です。モックでは該当する失敗データと状態選択肢を削除し、実Azureでの対象判別・取得継続はU3で検証します。アカウント探索が完了しない失敗では `totalAccounts` を `null` とし、探索できた件数と取得に成功した件数を混同しません。partial は6アカウント成功・15デプロイと、権限・通信・API・タイムアウトの4アカウント失敗を返します。

絞り込みの操作方式と候補の連動は第3節の合意に従います。テナント、サブスクリプション、リージョン、アカウント、モデルの5つの select は完全一致とし、デプロイ名は前後空白を除去して大文字・小文字を無視する部分一致とします。6条件は AND で組み合わせます。候補は取得に成功した行へ他の5条件を適用して生成し、そのプルダウン自身の条件だけを除外します。例えばテナントだけを選ぶと、そのテナントにあるサブスクリプション・リージョン・アカウント・モデルに候補が絞られ、テナント自身は別テナントへ切り替えられます。名前検索も候補に反映し、条件解除で候補を広げます。

名前入力や再取得で選択済みの値が候補から消えた場合、条件は自動解除せず「選択中（現在の条件に該当なし）」として表示します。この項目は選び直せない無効な項目とし、「すべて」または「すべて解除」で条件を外せます。候補を別の状態として保存せず、現在の取得結果と条件から画面描画時に計算します。自己条件の除外と選択済みの値が候補から消えた場合の表示も、モックの画面・操作の合意範囲です。

更新中は最初のアカウント応答まで前回結果を保持し、その旨を表示します。応答が届いたら今回の累積結果へ切り替え、以前のデータと混ぜません。進捗・途中結果・取得エラーは絞り込みと無関係に受け取り、表示時に現在の条件を適用します。一覧にはエラーの概要だけを表示し、詳細画面には今回受信済みの失敗を全件表示します。最終取得時刻は全件取得処理が完了した時だけ更新します。

取得要求は一意のIDを持ち、fetch境界が報告する段階・完了数・累積結果を、共通サービスが `DeploymentProgress` としてWails標準イベント `deployments:progress` で通知します。通知に要求IDと要求内の連番を付け、画面は現在の要求の新しい通知だけを反映します。取得完了後の通知、旧要求の進捗・成功・失敗・finally処理は現在の状態を上書きしません。生成した型を画面と共用し、最終結果は従来の呼出しの戻り値で確定します。途中通知用に別の画面・通信処理・定期的な取得は追加しません。

エラー通知は「4アカウントで取得失敗（一覧は不完全）」と「エラー詳細」を左側にまとめます。探索失敗は「対象の探索に失敗しました（一覧は不完全）」と表示し、未確定のアカウント件数を示しません。一覧見出しは通常「デプロイ 15件」、絞り込み中は「デプロイ 6 / 15件」とし、「取得に成功したデプロイのみ表示しています」という説明は重ねません。

モックの8状態（success、empty、partial、failure、cli-missing、all-accounts-failed、loading、delayed）は [mock.Provider](../internal/mock/provider.go) の固定データで再現します。通常応答は350ms、loading は30秒かけて進捗と途中結果を通知し、最後に success と同じ結果を返します。delayed は8秒かけて古い設定値を途中通知と最終結果に含めます。成功・空・部分失敗・全アカウント失敗でも同じ通知契約を使います。待ち時間の1/5を5サブスクリプションの探索、4/5を10アカウントの取得に割り当て、元の配列順とは異なる固定の応答到着順を再現します。実Azureの並列取得処理をモック内へ作り込みません。モックの応答時間を実 Azure の取得性能の証拠として扱いません。モックの画面・操作は合意済みです。実Azureの取得時間は[高速化の検証結果](#f1-azure-performance)に記録済みで、許容時間と既定表示範囲の合意はU3に残ります。
