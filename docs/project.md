## モデル追加（2026-09-14・仮UI確認中）

主ユースケースを「モデルを追加する」とし、必要時に「Foundryを追加する」が拡張し、それを「リソースグループを追加する」が拡張します。以下は旧F2独立参照・F3範囲案に優先します。F1の一覧・絞り込みは維持します。利用者の最終動作合意はまだありません。

| シナリオ | 操作と期待結果 |
| --- | --- |
| F3-S1 | 一覧見出し右端の「＋ 新規追加」からサブスクリプション・RG・Foundryを選び、モデル・バージョン・SKU・Capacity・デプロイ名を設定する。デプロイ0件のFoundryでも開始可能。 |
| F3-S2 | Foundry新規作成で名前・リージョンを入力し、モデル追加に戻って作成予定として選択する。 |
| F3-S3 | Foundry追加内または配置先の選択欄からRGを新規入力し、呼出元に戻る。Foundry入力中の名前を保持する。 |
| F3-S4 | 上位の選択変更で下位の選択を解除する。確認から戻ると入力を保持し、追加全体を閉じると破棄する。 |

### 入力と表示

- U1確認用の旧モックは固定候補の既定バージョン・SKUを自動設定する。U4追加モックでは[作成契約案](#f3-create-contract)に従い、形式・名前・バージョン・SKUの組合せを保持し、一意な既定版と、Globalを優先したSKUを初期選択する。どちらもモデル名と同じデプロイ名を初期入力し、手動変更できる。
- 新規名は[Azureの命名規則](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/resource-name-rules)に基づく。Foundryは2〜64文字の半角英数字・ハイフン、先頭末尾は英数字。RGは1〜90文字のUnicode文字・十進数字・アンダースコア・ハイフン・ピリオド・括弧、末尾ピリオド禁止。同一スコープの固定候補との重複は大文字小文字を区別せず拒否する。Azure側の使用可否照会は行わない。
- RG・Foundry名に入力モードurl、自動大文字化・自動訂正・スペルチェック無効を指定する。[入力モード指定](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/inputmode)はOSのIME強制OFFを保証しない。Windowsでの実際の切替は未検証。
- 重複した説明・手順見出しを省き、一覧の追加ボタンは件数と同じ行の右端へ置く。モックの補助操作は入力欄の後ろに置く。
- ダイアログ・候補取得状態・名前の補足／エラー・一覧の取得状態に必要な領域を確保し、非同期状態で既存入力欄を動かさない。フォーカスは内側の枠とし、スクロール境界で切れる外側の太い二重枠を廃止する。ネイティブselectとキーボード操作は維持する。画面規則は[frontend/src/AGENTS.md](../frontend/src/AGENTS.md)。

### U4 実処理へ接続する設計案（2026-09-15・未合意）

推奨は、既存Foundryでは現在のGo `ModelService.GetModels(accountID)` を使い、新規Foundryではリージョン単位の候補を先に参照し、作成後に同サービスで選択内容を再確認する方式です。「最後に作成予定を確認する」という仮UIの操作順を保ち、候補を見るためだけにリソースを残すことを避けられます。以下は調査に基づく案であり、採用合意・実装・実作成の承認ではありません。

#### 外部契約と再利用範囲

[Accounts List Models](https://learn.microsoft.com/en-us/rest/api/microsoftfoundry/accountmanagement/accounts/list-models?view=rest-microsoftfoundry-accountmanagement-2025-06-01)は既存アカウントを必要とします。一方、[Models List](https://learn.microsoft.com/en-us/rest/api/microsoftfoundry/accountmanagement/models/list?view=rest-microsoftfoundry-accountmanagement-2025-06-01)はサブスクリプションとリージョンを指定して取得でき、アカウント作成を前提としません。両者は応答形式と対象範囲が違うため、リージョン候補を特定Foundryでの作成可否の保証には使いません。

2026-09-15、指定サブスクリプションのJapan EastをAPI 2025-09-01で読み取りました。リージョン候補は218行（AIServices 109、MaaS 61、MAI 1、OpenAI 47）、既存AIServicesアカウント `nuits-japaneast` の候補は109行でした。リージョン候補をkind=AIServicesで絞った109行は、形式・名前・バージョン・内側のSKU名で今回のアカウント候補と一致しました。1リージョン・1アカウントの観測であり一般保証ではありません。外側の `skuName` はこの応答ではすべてS0で、アカウントSKUを指します。デプロイSKUは内側の `model.skus[].name` を使います。

既存の[ModelService](../internal/service/models.go)と[Azure境界](../internal/azurego/provider.go)の認証・対象検査・ページング・失敗返却を再利用します。新規用には同サービスへリージョン候補の取得入口とAzure境界の変換を加える案です。デプロイ一覧の行を配置先一覧の正本にせず、RG・Foundryを独立に探索し、デプロイ0件も選べるようにします。新しい汎用サービス基盤や別系統の画面は追加しません。

現行F2の画面向け型はモデル・バージョンごとにSKU名だけを保持し、容量制約を捨てています。F3では同サービスの型を拡張し、モデル形式・名前・明示バージョン・SKUごとの容量制約を保持する必要があります。[2025-09-01のデプロイ契約](https://learn.microsoft.com/en-us/azure/templates/microsoft.cognitiveservices/2025-09-01/accounts/deployments)ではバージョン省略時に可変の既定版が割り当てられるため、確認画面に出したバージョンを明示して送る案です。SKUの既定値を配列先頭から推測せず、Capacityの許可値・最小・最大・刻み・既定値を取得できる範囲で使います。欠損時にモックの固定値10で補完しません。取得できない制約は個別に確認する必要があります。

#### 作成順序と結果の確定

1. 既存Foundryではアカウント候補、新規Foundryでは指定リージョンの候補を取得し、モデル・バージョン・SKU・Capacityを入力する。新規候補は暫定であることを示す。
2. 対象の完全なリソースID、既存／新規、リージョン、費用条件、失敗・中断後に残るリソースを確認する。この時点までAzureへ書き込まない。
3. 承認後、必要なRGを作成し、新規Foundryを作成する。RGが既存なら使用するだけで更新しない。Foundryの非同期処理の完了を待つ。
4. 作成したFoundryの候補を既存ModelServiceで取得し、選択した組合せと容量制約を再検査する。候補がない・変わった場合は停止し、作成済みのFoundryを明示して再選択と再確認へ戻す。別モデル・SKU・容量へ自動変更しない。
5. 同じFoundry内のデプロイ名を再照会し、既存名を拒否する。競合防止条件が解決してから作成要求を送る。非同期処理の成功とGETで設定を照合して完了とし、その後一覧を再取得する。一覧再取得だけの失敗では作成を再実行しない。

画面は入力と確認状態を保持し、Goサービスが要求対象・送信済み段階・結果を管理します。Azure境界がSDKの非同期処理とGET照合を担当し、画面のタイムアウトだけでAzure側の成否を確定しません。RG・Foundry・デプロイは一括トランザクションではなく、成功済み段階を後続失敗で取り消しません。

| 状態 | 残るものと停止範囲 | 再開方法の案 |
| --- | --- | --- |
| 確認前にキャンセル | Azureには何も作られない。 | 現行モックどおり入力を破棄する。 |
| RG成功、Foundry失敗 | 作成済みRGが残る。Foundryの失敗したリソースも残る可能性があり、GETで調べる。後続デプロイ要求は送らない。 | RGとFoundryの完全ID・観測状態を表示する。既存RGとして選び直せても、失敗したFoundryへのPUTは自動再送しない。 |
| Foundry成功、候補取得・再検査・デプロイ失敗 | 新規作成したRGとFoundryは残る。既存なら「既存」と区別する。デプロイ送信後の失敗では失敗状態のデプロイも残り得る。 | 候補の再取得・再選択後、未送信のデプロイ段階だけを再確認できる。送信済みで失敗した段階は状態照会して停止する。 |
| 送信後のキャンセル・切断・タイムアウト | Azure側で進行中または完了している可能性がある。キャンセルをロールバック完了とは扱わない。 | 「結果不明」とし、同じIDの処理状態と設定を読み取る。PUTを即再送しない。 |
| 作成成功、一覧更新失敗 | 作成済みデプロイは残る。 | 作成成功と表示更新失敗を分け、一覧の読取のみ再試行する。 |

[Azureの非同期操作](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/async-operations)に従い、送信応答から得た本操作の処理URLと状態を追跡します。本操作に対応する終端成功の応答と、完全IDへのGETによる期待設定の一致がそろった時だけ成功とします。リソースの `provisioningState=Succeeded` や設定一致だけでは、別操作による作成・更新と区別できません。処理が進行中なら監視を再開し、不一致なら競合として停止します。初回応答や操作との対応を失った場合、処理URLが期限切れになった場合は結果不明を維持します。一度の404も未作成確定の根拠にしません。終端失敗は残骸の不存在を意味せず、失敗した対象の存在・状態も再照会します。

アプリ終了後の照合方法と送信境界は[操作記録と再開](#f3-operation-record)の案とします。再試行で別名を自動生成せず、自動削除もしません。画面の「再試行」は読取再開と書込再送を区別します。

#### 重複作成と実作成前の条件

[Deployments Create Or Update](https://learn.microsoft.com/en-us/rest/api/microsoftfoundry/accountmanagement/deployments/create-or-update?view=rest-microsoftfoundry-accountmanagement-2025-06-01)は同じIDを更新できるPUTです。事前のGETで存在したら拒否し、403や通信失敗を不存在と扱いません。ただし不存在確認後、他の操作が同名を作る競合は残ります。公開REST契約と固定SDKで条件付き作成ヘッダーの対応を確認できていないため、`If-None-Match: *`を付ければ上書きを防げると仮定しません。外部操作との競合を防ぐ方法を確定・検証するか、その限界を明示した作成条件に合意するまでは実作成へ進みません。

実検証には指定サブスクリプションを使用しますが、RG・Foundry・リージョン・モデル／バージョン・SKU・Capacity、許容費用と保持期間、削除条件は未合意です。Foundry設定は[作成契約案](#f3-create-contract)に具体化しましたが、採用合意ではありません。候補の存在やCapacityは見積金額を意味しません。これらの決定前に作成・削除を行いません。

受け入れ検証では、上表の各失敗位置、送信直後の応答喪失、再起動後照合、二重クリック、同名の外部作成、候補の変化、一覧更新失敗を再現します。結果表示と読取再試行のモックは[追加モックの記録](#f3-u4-review)に従います。モックの動作合意後に実処理を接続し、承認された専用対象で実検証します。永続化・再起動後照合と実処理は未実装・未検証です。

#### 操作記録と再開の具体案

### U5 命名規則と重複の調査（2026-09-15）

[Azure正式命名表のMicrosoft.CognitiveServices節](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/resource-name-rules#microsoftcognitiveservices)にはaccountsの規則があり、accounts/deploymentsの行はありません。[公式OpenAPI 2025-09-01](https://github.com/Azure/azure-rest-api-specs/blob/6bbb6daca7175b2cab69b20b2dd01094e3c6a534/specification/cognitiveservices/resource-manager/Microsoft.CognitiveServices/stable/2025-09-01/cognitiveservices.json)の `deploymentNameParameter` も必須stringのみで、最小長・最大長・許可文字の定義がありません。accountNameの2〜64文字やパターンをdeploymentNameの規則として転用する根拠にはできません。

したがって、現行モックの2〜64文字・半角英数字・アンダースコア・ハイフン・ピリオドという入力規則は、合意済みの暫定UI規則として維持します。Azure正式規則としての確定は未了です。RPの正式な検証仕様を追加確認し、読取だけで確定できなければ、費用・対象・条件を承認した後の境界値検証が必要です。この調査結果を理由に合意済み入力規則を変更していません。

同名デプロイは同一Foundry配下の同じリソースIDになるため、追加時には大文字小文字を区別せず既存名を拒否する案です。別Foundryの同名は許容します。画面の事前検査と送信直前のGo側照会を行い、既存デプロイへの更新に切り替えません。U4追加モックでは `contoso-chat-prod` の既存名 `chat-production` を固定データとして保持し、画面の重複拒否を実装・headless検証しました。Go側の実照会・競合防止は未実装です。競合と結果不明時の扱いは[U4設計案](#f3-u4-design)に従って確定します。

Windows版Azure CLIの標準出力・標準エラーは、[CLI境界](../internal/azurego/cli_windows.go)でWindowsの既定ANSIコードページからUTF-8へ変換してから使用します。2026-09-13、この環境のMSI版ランチャーはPythonを`-I`（隔離モード）で起動し、実際のパイプ出力はCP932でした。[Pythonの標準入出力仕様](https://docs.python.org/3.14/library/sys.html#sys.stdout)に合わせて`GetACP`でコードページを取得し、[MultiByteToWideChar](https://learn.microsoft.com/en-us/windows/win32/api/stringapiset/nf-stringapiset-multibytetowidechar)の`MB_ERR_INVALID_CHARS`で厳密変換します。不正バイトを黙って置換せず、変換失敗を取得エラーにします。文字コードの推測や、`chcp`・OS設定・Azure CLI設定の変更は行いません。既存の`golang.org/x/sys`を直接利用し、新規依存は追加していません。CLIの配布方式やPythonの既定文字コードが変わる場合は、この入出力契約を再検証します。

### レート制限の外部仕様の確認

2026-09-13、Microsoft の [Deployments List（API 2025-06-01）](https://learn.microsoft.com/en-us/rest/api/microsoftfoundry/accountmanagement/deployments/list?view=rest-microsoftfoundry-accountmanagement-2025-06-01) を確認しました。応答には `sku.capacity`、`properties.rateLimits`、`properties.callRateLimit` が定義されていますが、直接 `tpm` / `rpm` という名前の項目はありません。F1 の表示契約では `properties.rateLimits` の `key` が `token` の値を TPM、`request` の値を RPM とし、`count` と `renewalPeriod` から1分あたりへ正規化します。欠損・不正値・1分あたりに整数化できない値は不明のままにします。

[クォータの公式資料](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/quota) は、容量単位と TPM/RPM の対応がモデルにより異なると説明しています。また、[Provisioned の容量](https://learn.microsoft.com/en-us/azure/foundry/openai/concepts/provisioned-throughput) は PTU で扱われます。このため、`sku.capacity` の生値を TPM として表示したり、全モデル・SKU に一律の換算を適用したりしません。実接続では11デプロイを取得し、11件のRPM、10件のTPMを `rateLimits` から表示でき、TPM欠損の1件は不明になりました。Portal の設定値との照合、別モデル・SKUおよびページング境界の網羅性は U3 の残件です。

取得要求の単位: アカウント探索に使う Resources List はサブスクリプション単位、[Deployments List](https://learn.microsoft.com/en-us/rest/api/microsoftfoundry/accountmanagement/deployments/list?view=rest-microsoftfoundry-accountmanagement-2025-06-01) はアカウント単位で、どちらも複数ページになり得ます。このAPI構造を踏まえ、進捗はHTTP要求数ではなく各対象の全ページ取得の完了数で扱います。失敗で終了したアカウントとデプロイ0件の成功も完了数に含めます。探索とデプロイ取得では総作業量が異なるため、全工程を通した推測のパーセントは表示しません。

実Azureの探索進捗では、権限不足で対象外になったサブスクリプションを完了数・総数に含めず、その対象の進捗通知も発行しません。除外対象の判別が終わるまで総数を未確定とし、全探索応答の処理後に対象内の件数を確定します。認証・通信エラーは対象内の失敗として件数と失敗情報に保持します。

### F1 モックの構成と画面

本番用の [DeploymentService](../internal/service/deployments.go)、`GetDeployments`、`GetEnvironment`、[React 画面](../frontend/src/App.tsx)、および [生成した TypeScript 型・呼出し](../frontend/bindings/github.com/nuitsjp/azfoundry-deck/internal/service/deploymentservice.ts) を共用し、Azure 境界の fetch 関数だけを [mock.Provider.Fetch](../internal/mock/provider.go) に置き換えます。[モック専用サービス](../internal/mock/service.go) の `NewMockService(provider).SetScenario` は次回取得の状態だけを設定し、選択しただけでは取得を開始しません。モック専用の状態設定を本番の `DeploymentService` に持ち込みません。

一覧とエラー詳細は同じ取得結果を参照します。一覧から「エラー詳細」で遷移しても取得せず、「デプロイ一覧に戻る」では結果、絞り込み条件、最終取得時刻を保持します。エラー詳細画面の画面名は「エラー詳細」とし、失敗アカウントまたは探索対象、コード、理由、対処を全件表示します。両画面上部のモック状態切替と更新は共通の次回取得状態を設定し、詳細画面で成功更新した場合は「取得エラーはありません」と表示します。

ブラウザーの再読み込み時は、モック専用の `GetScenario` で現在の設定を読み、選択欄と取得結果を一致させます。Windows版とブラウザー版の違いは Wails のビルドタグだけで、どちらも同じ画面、型、生成バインディング、Goサービス、固定データを使います。

Wails serverモードの書き込み制限は、30秒の読込中シナリオを完了まで再現できるよう45秒に設定しています。既定値30秒とモックの待ち時間が同じで、応答を返す前に制限へ達するためです。実Azureの取得タイムアウトを合意したものではありません。

固定データは3テナント、5サブスクリプション、10アカウント、24デプロイです。成功シナリオでは同名デプロイを複数アカウントに置き、各行の `id` と完全なアカウントARMリソースIDで区別します。`tpm` と `rpm` は `*int64` から `number | null` として生成し、欠損は `null` のまま返します。値は SKU の Capacity やモデル別の換算から求めず、画面確認用に独立して設定した架空値です。JSON の `deployments` と `failures` は常に空配列または要素を持つ配列で、`null` にはしません。`failures` は対象範囲内の失敗アカウントまたは探索対象、コード、理由、対処を保持します。対象外のテナント権限不足はfetch境界で除外し、この結果へ含めない契約です。モックでは該当する失敗データと状態選択肢を削除し、実Azureでの対象判別・取得継続はU3で検証します。アカウント探索が完了しない失敗では `totalAccounts` を `null` とし、探索できた件数と取得に成功した件数を混同しません。partial は6アカウント成功・15デプロイと、権限・通信・API・タイムアウトの4アカウント失敗を返します。

絞り込みの操作方式と候補の連動は第3節の合意に従います。テナント、サブスクリプション、リージョン、アカウント、モデルの5つの select は完全一致とし、デプロイ名は前後空白を除去して大文字・小文字を無視する部分一致とします。6条件は AND で組み合わせます。候補は取得に成功した行へ他の5条件を適用して生成し、そのプルダウン自身の条件だけを除外します。例えばテナントだけを選ぶと、そのテナントにあるサブスクリプション・リージョン・アカウント・モデルに候補が絞られ、テナント自身は別テナントへ切り替えられます。名前検索も候補に反映し、条件解除で候補を広げます。

名前入力や再取得で選択済みの値が候補から消えた場合、条件は自動解除せず「選択中（現在の条件に該当なし）」として表示します。この項目は選び直せない無効な項目とし、「すべて」または「すべて解除」で条件を外せます。候補を別の状態として保存せず、現在の取得結果と条件から画面描画時に計算します。自己条件の除外と選択済みの値が候補から消えた場合の表示も、モックの画面・操作の合意範囲です。

更新中は最初のアカウント応答まで前回結果を保持し、その旨を表示します。応答が届いたら今回の累積結果へ切り替え、以前のデータと混ぜません。進捗・途中結果・取得エラーは絞り込みと無関係に受け取り、表示時に現在の条件を適用します。一覧にはエラーの概要だけを表示し、詳細画面には今回受信済みの失敗を全件表示します。最終取得時刻は全件取得処理が完了した時だけ更新します。

取得要求は一意のIDを持ち、fetch境界が報告する段階・完了数・累積結果を、共通サービスが `DeploymentProgress` としてWails標準イベント `deployments:progress` で通知します。通知に要求IDと要求内の連番を付け、画面は現在の要求の新しい通知だけを反映します。取得完了後の通知、旧要求の進捗・成功・失敗・finally処理は現在の状態を上書きしません。生成した型を画面と共用し、最終結果は従来の呼出しの戻り値で確定します。途中通知用に別の画面・通信処理・定期的な取得は追加しません。

エラー通知は「4アカウントで取得失敗（一覧は不完全）」と「エラー詳細」を左側にまとめます。探索失敗は「対象の探索に失敗しました（一覧は不完全）」と表示し、未確定のアカウント件数を示しません。一覧見出しは通常「デプロイ 15件」、絞り込み中は「デプロイ 6 / 15件」とし、「取得に成功したデプロイのみ表示しています」という説明は重ねません。

モックの8状態（success、empty、partial、failure、cli-missing、all-accounts-failed、loading、delayed）は [mock.Provider](../internal/mock/provider.go) の固定データで再現します。通常応答は350ms、loading は30秒かけて進捗と途中結果を通知し、最後に success と同じ結果を返します。delayed は8秒かけて古い設定値を途中通知と最終結果に含めます。成功・空・部分失敗・全アカウント失敗でも同じ通知契約を使います。待ち時間の1/5を5サブスクリプションの探索、4/5を10アカウントの取得に割り当て、元の配列順とは異なる固定の応答到着順を再現します。実Azureの並列取得処理をモック内へ作り込みません。モックの応答時間を実 Azure の取得性能の証拠として扱いません。モックの画面・操作は合意済みです。実Azureの取得時間は[高速化の検証結果](#f1-azure-performance)に記録済みで、許容時間と既定表示範囲の合意はU3に残ります。
