# 設計・文書作成の標準

標準 ID: `project-template-design-and-documentation` / 版: **2**

<a id="implementation-principles"></a>
## 1. 適用原則

現在の要件を満たす最小限かつ最も単純な構成から着手します。既存機能の活用・ライブラリ導入・独自実装を、コードや文書の量だけでなく、理解・実装・変更・検証・運用の総負担で比較します。

- 依頼範囲外の機能追加、無関係なリファクタリング、汎用化を目的とした過剰な共通基盤は作成しない。
- 後方互換性やフォールバックは、明示的な要件がある場合のみ実装する（暗黙の代替補完は行わない）。
- 性能改善は計測結果に基づき、ボトルネックに限定して実施する（推測による先行対策は行わない）。
- 入力検証はシステム境界（ユーザー入力・外部連携等）で行い、内部での重複検査や過剰な防護は避ける。
- テストは期待される振る舞いと実際のリスクを検証する（実装の形式的な追認や網羅率のみを目的とした作成は避ける）。

<a id="design-decisions"></a>
## 2. オーバーエンジニアリングの抑止

新しい層、抽象化、依存ライブラリ、外部サービス、運用機構を追加する場合は、以下を説明できることを条件とします。

1. 現在の要件や確認済みリスクの何に対応するか。
2. 導入しない場合、具体的にどのような問題が生じるか。
3. 局所的な修正、より単純な構成、手動運用ではなぜ不十分か。
4. なぜ今必要であり、導入・保守・運用の総負担を受け入れられるか。

将来要件への対応は現時点の必要性を個別に判断し、根拠が不十分な場合は計画への記録にとどめて実装を見送ります。

<a id="document-roles"></a>
## 3. オーバードキュメンテーションの抑止

決定事項の正本は1箇所に集約し、仕様の重複記述を排除します。

- **新設・分割の基準**: 読者と判断目的が明確で、既存正本への追記では不十分な場合のみ新設します。コードから自明な内容の説明や、他文書の転記は行いません。
- **記入欄の取捨選択**: 判断に必要な項目のみを使用し、該当しない項目は削除できます（非該当の理由が判断に必要なら記録）。推測による未確定事項の追加は避けます。
- **必要な情報の維持**: 要求、根拠、責務、障害時の動作、検証条件など、実装や受け入れ判断に必要な情報は省略しません。

| 情報の種類 | 記録内容 |
| --- | --- |
| 事実 | 情報源、対象版、確認範囲（仮定と明確に区別） |
| 合意 | 決定内容、範囲、判断者、日付、根拠 |
| 実装 | 仕様とコードの対応関係（コードの存在自体は合意・検証を意味しない） |
| 検証 | 実行条件、対象版、結果、証跡（未検証項目を合格扱いにしない） |

未決事項は一意な ID、前提、影響範囲、解消条件で追跡します。過去の文書や実装は参考証跡として扱い、現行仕様へ暗黙的に引き継ぎません。

<a id="architecture-method"></a>
## 4. 必要な設計の具体化

1. 対象機能の入力、期待結果、外部仕様の事実を確認する。
2. システム・実行・保存・信頼の境界と責務を整理する。
3. 主要シナリオから、状態更新の担当、結果確定点、障害時の停止・継続範囲を明確にする（競合や通信断が想定される場合はトランザクション境界も定義）。
4. 追加する仕組みの根拠と検証方法を定め、受け入れ条件と照合する。

図法や章構成は固定しません。文章や表で十分ならそれを活用し、構造や時系列の理解を助ける場合のみ図を追加します。

<a id="completion"></a>
## 5. 判断の記録と完了基準

設計判断の理由は該当箇所の近くに簡潔に記録します。ADR（設計判断記録）は「変更負担が大きい」「理由が非自明」「重要なトレードオフがある」のすべてを満たす場合のみ作成します。

- **設計の完了条件**: 主要シナリオについて、データ整合性、状態更新の主体、結果確定点、障害時の停止・継続範囲、および検証方法が明確になった時点で設計完了とします。
- **機能の完了条件**: 合意範囲の実装、必要なテストおよび実環境検証の合格、必須修正の解消をもって完了とします（モック合意やコード作成のみでは未完了）。
- **レビュー指摘の分類**: 指摘は「必須修正（要件充足に必須）」「任意改善（完了を妨げない）」「対象外」に分類します。必須修正が残る場合は未完了とし、合意済みのリスク受容事項を根拠なく再審議しません。

<a id="agreement-changes"></a>
## 6. 合意を保護する変更手続き

1. 着手前に、採用基準、正本の責務、保護する合意、および依頼範囲を確認する。
2. 合意済みの要件・制約・仕様を変更・緩和する場合は、変更内容・理由・影響を明示し、合意を得てから適用する（表現の改善や承認済みの変更に対する再承認は不要）。
3. 完了前に、着手時の合意との差分、検証結果、正本間のリンク整合性を確認する。

変更の検討や調査は先行して進め、ユーザー判断が必要な事項のみを整理して提示します。
