# モック駆動開発の標準

標準 ID: `project-template-mock-driven-development`

## 1. 目的と適用

最小限の動作するモックで操作・入出力・状態の認識を合わせ、合意した仕様を実現パターンに沿って実処理へ接続します。適用範囲は [文書方針](../document-policy.md#mock-scope) に従います。

仕様合意用モックとテスト用のスタブ・モックは目的が異なり、テスト用モックの存在をもって仕様合意とはみなしません。

<a id="workflow"></a>
## 2. 系列ごとの実施手順

各フェーズでは、エージェントが作業を終えてコミットし、利用者に確認を依頼して停止します。承認されれば次のフェーズへ進み、差し戻されれば指示されたフェーズで修正して確認を依頼し直します。承認後に残す作業は置きません。

| # | フェーズ | エージェントの作業 | 確認を依頼する条件 | 利用者の確認 |
| --- | --- | --- | --- | --- |
| 1 | 仕様検討 | 系列用の作業ブランチを作り、対象系列の全文を書いてコミットする（初回は主アクター、目的、前提、主成功系列、受け入れ条件、実現パターンの割り当て。初利用のパターン案も含む。2回目以降は拡張1本） | 雛形どおりに記載し、`scripts/doc_check.py` が NG なく通る | 変更ファイル、UI 確認の要否、論点 |
| 2 | モック確認 | UI 確認が必要な系列のみ実施する。本番の型・契約を共有する合成点1箇所で固定データに差し替え、振る舞いの論点を既定案でシナリオへ反映してコミットする。モック有効でアプリを起動し、確認手順を自動実行する（Web UI では Playwright CLI） | 提示コミットから同一固定データで繰り返し再現でき（失敗分岐・再試行・部分成功は UI の振る舞いを決める場合のみ）、自動実行が合格し、アプリが起動している | 起動中のアプリでの対象系列の振る舞い、変更ファイル、論点 |
| 3 | テーブル設計 | テーブルを追加・変更する系列のみ実施する。[設計標準第4節](design-and-documentation.md#architecture-method) に従って `docs/design/data.dbml` に設計を書き、コミットする | 責務と関係、カラムと型、制約が示され、DBML の構文検証が通っている | 変更差分の ER 図、変更範囲、論点 |
| 4 | 実装 | 合意した入出力を維持し、画面、業務処理、外部接続、DB 操作・永続化・マイグレーション、必要なエラー処理を含む対象系列の実装をすべて完了する。固定データを外部システム境界側へ移すか削除し、役割表に実装パスを記録してコミットする。モック無効でアプリを起動し、確認手順を自動実行する | 未実装・未接続の処理がなく、実行経路に仕様合意用モックやフォールバックが残らず、既存テストと自動実行が合格し、アプリが起動している | 起動中のアプリでの完成系の監査、変更ファイル、論点（E2E テストは未作成） |
| 5 | 仕様固定 | 承認された振る舞いと受け入れ条件を E2E テストで固定し、E2E で検証しにくいリスクに限り単体・結合テストで補強する。実環境で検証し、PR を作成して CI の合格まで対応する | CI と、資格情報や実機 GUI を要する手元の検証が合格している | PR と CI の結果、次の系列の提案（拡張の追加またはユースケースの完了） |

確認の依頼では、番号ではなくフェーズ名で対象を示し、提示コミット、変更ファイルの一覧、論点を伝えます。モック確認と実装では確認目的、簡潔な手順、期待結果を加え、Web UI では URL を示します。論点は選択によって利用者が得る価値が変わる点に限り、件数は制限せず、文言や実装内部の選択は含めません。各論点の既定案は文書と実装へ反映済みとし、全文は変更ファイルと差分で確認できるようにします。返答は「承認」または「差し戻し: 指摘内容」とし、仕様固定では PR のマージを承認とします。

<a id="discussion"></a>
### ユースケース案の記載と確認

1. 仕様検討では、案の全文を `docs/usecases/<名称>/README.md`、対象の `scenarios/<名称>.md` と必要な一覧・関連設計へ直接書いてコミットします。[作成用スキル](../../.agents/skills/usecase-docs/SKILL.md) の文書構造と雛形に従い、系列は1ファイルずつ記載します。
2. メッセージには変更ファイルの一覧と論点だけを示し、全文や要約は転記しません。差し戻し時はファイルを修正し、改めて一覧と論点を示します。
3. 承認は会話での明示的な「承認」に限り、質問・修正指示・無応答を承認と扱いません。ユースケース一覧だけの検討や合意済み仕様の変更にも同じ手順を適用します。

- **ユースケースの分割**: ユースケースは「1つの主アクターの1つの目的」単位とし、条件分岐を含まない主成功系列を1本定義します。API、画面、データ取得の単位では分割しません。条件差異は主成功系列の途中から分岐する拡張系列として着手時に1本ずつ追加します。単独で目的を達成する系列は別ユースケースとし、拡張の本数を理由に分割したり、未着手の拡張を先回りして列挙したりしません。条件とメッセージだけが異なる場合は拡張を増やさず、条件と対応するメッセージを仕様に列挙します。利用者の操作・画面遷移・状態の変化が異なる場合のみ別の拡張とします。UI 確認が必要な系列を含むユースケースをモック対象とします。
- **実行手順の記録**: `docs/project.md` 第5節に環境構築、作業ディレクトリ、実行コマンド、設定、成功確認、モックの起動・終了と有効/無効の確認、実処理への切り替えを記録します。接続失敗時にモックへフォールバックしないことも確認します。
- **作業単位と仕掛かり上限**: 1本の系列を仕様検討から仕様固定まで通すことを作業単位とし、1つの作業ブランチと PR にまとめます。完了するまで次の系列やユースケースには着手しません。セッションをまたぐ場合も同じ系列を継続し、会話の文脈と現在の仕様・実装から対象とフェーズを確認します。承認が不明なら利用者に確認し、文書・コード・テストの存在だけで承認済みと扱いません。再開用の計画・進捗文書は作りません。仕様固定ではビルドと E2E テストを1コマンドで再実行できるようにし、CI で同じコマンドを実行します。資格情報や実機 GUI を要する検証は手元で実行して会話で結果を報告します。
- **テストコードの追加・更新時点**: 新規テストと既存テストにない検証の追加は、単体・結合・E2E を問わず、実装フェーズで完成系の承認を得た後の仕様固定で行います。それまでは手動で確認します。ただし、合意済みの仕様変更で陳腐化した既存テストの期待値の置換は、実装フェーズで本番実装と同時に行い、既存テストの合格を維持します。仕様固定では合意シナリオと受け入れ条件を E2E で検証します（UI 確認不要の系列も同様とし、全ユースケース完了まで延期しません）。シナリオの E2E は `<ユースケース名>/<シナリオ名>.<拡張子>` の1ファイルに置き、`開始条件`（拡張は `分岐条件`）、手順表の各行に対応する `手順1`〜`手順N`、`受け入れ条件` をラベルとする区切りで記述します。各手順の区切りでアクターの操作とシステムの振る舞いを検証し、共通の受け入れ条件は該当シナリオの `受け入れ条件` で検証します。シナリオに記載のない振る舞いは、拡張シナリオとして合意・文書化してから検証を追加します。合意した振る舞いのうち E2E で検証しにくいリスク（並列、境界値、障害時動作）に限り、単体・結合テストで補強します。仕様固定で本番実装の変更が必要になった場合は E2E の追加を中断し、実装フェーズに戻って修正後の完成系の承認を再度得ます。E2E は対象システムの入口から結果までを検証し、具体的なツールは採用プロジェクトで選びます。既存テストは各フェーズで実行し、先行して完了した系列の E2E テストも維持します。後続系列の実装フェーズで先行系列のテストが失敗した場合、合意済み仕様を変えない修正はそのまま行い、仕様変更を伴う場合は先行系列の再合意を先に得ます。
- **ユースケースの完了**: 記述済みの全系列が仕様固定を終え、追加する拡張がないことを仕様固定の確認で利用者が承認した時点です。
- **確認待ち中の作業**: 仕様検討の確認待ち中は読み取り調査にとどめます。モック確認の確認待ち中は、当該系列の UI・系列や未合意のテーブル設計に依存しない部分（外部接続の実装・実測）のみ進められます。未合意のテーブル設計に依存する保存処理やマイグレーションは実装しません。フェーズは進めず、他系列・ユースケースには着手しません。確認で内容が変わった場合は、影響箇所を修正します。
- **モック対象の絞り込み**: UI 確認は、利用者の操作・入出力・状態の振る舞いを動かして仕様を決定する必要がある系列に限定します。条件とメッセージだけが異なる系列は、条件と対応するメッセージを仕様に定めれば足り、個別の再現は不要です。拡張の本数を理由にしたユースケース分割は行いません。
- **フェーズの省略**: UI 確認が不要な系列はモック確認を、テーブルを追加・変更しない系列はテーブル設計を省略します。省略は、必要な仕様合意・実装・検証の省略を意味しません。
- **仕様変更**: 合意済みの内容を変更する場合は、文書を書き換えてコミットし、変更の理由・影響と論点を示して承認を得ます。途中案、修正指示、論点への回答、承認原文は文書へ転記しません。

<a id="boundaries"></a>
## 3. モックを作り込みすぎない

- 置き換え境界は、本番の型・契約を共有でき、反復が最も速い合成点1箇所とします（UI 側でも可。当該境界に実処理があれば利用します）。
- モック専用の型・画面・通信層は作成せず、固定データは算術生成、業務ロジックや永続化の再実装を含まない固定表とし、本番の型で管理します。
- 固定データは実装フェーズで外部システム境界側へ移すか削除し、重複保持しません。
- 本番構成ではモックを無効化し、実処理失敗時のモックへのフォールバックは禁止します（切り替えは合成点1箇所、既定は実処理）。
- モックツールの選定は素朴なモックで不足した時点で行い、理由と保守負担は会話で説明します。文書には採用した構成と実行手順だけを反映します。

## 4. 記録先

モック専用の仕様書は新設せず、既存の正本で管理します。

| 正本 | 記録内容 |
| --- | --- |
| `docs/usecases/<名称>/README.md`（[一覧](../project.md#usecases) から参照） | 現在のユースケースの共通事項とシナリオへの個別リンク |
| 上記と同じディレクトリの `scenarios/<名称>.md` | 系列の条件・手順・受け入れ条件、種別、UI確認の要否 |
| `docs/design/UCP-n.md` | パターンごとのモック境界と合成点、役割と実装パス |
| `docs/design/data.md`、`docs/design/data.dbml` | 現在の保存形式と型の対応、DBML によるテーブル設計 |
| プロジェクト定義 第5節 | 起動・終了・モック有効/無効の確認・実処理への切り替え・テストの実行手順と期待結果 |

モックでの合意は実処理の正常動作（保存・認証・性能・耐障害性など）を保証しません。必要な検証は実環境・実処理で実施し、未検証のユースケースを完了扱いにはしません。
