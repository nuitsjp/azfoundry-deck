# モック駆動開発の標準

標準 ID: `project-template-mock-driven-development` / 版: **2**

## 1. 目的と適用

最小限の動作するモックで操作・入出力・状態の認識を合わせ、合意した仕様を実処理へ接続します。適用範囲はプロジェクトの [文書方針](../document-policy.md#mock-scope) で定めます（特定の画面技術やツールは強制しません）。

仕様合意用モックとテスト用のスタブ・モックは目的が異なり、テスト用資産の存在をもって仕様合意とはみなしません。

<a id="workflow"></a>
## 2. 機能ごとの実施手順

| 順序 | 実施内容 | 次へ進める条件 |
| --- | --- | --- |
| 1. シナリオ定義 | 仕様の正本に ID、初期条件・入力、操作・契機、期待結果を定義。未確定事項は計画書の課題 ID と紐付ける | 確認対象とモック再現範囲が明確である |
| 2. モック作成 | 本番の入出力処理を共用し、外部呼出などの境界のみ固定データに置き換える。状態再現手順を用意する | 同一シナリオを同一条件で繰り返し再現できる |
| 3. 動作合意 | 再現手順、対象版、シナリオ、判断事項を提示し、仕様の正本へ合意（判断者・日付・根拠）を記録する | 実装対象の仕様が合意されている |
| 4. 実処理接続 | 合意した入出力を維持しつつ実処理へ接続。モック無効化環境で同一の期待結果を確認する | 実接続先が利用され、モックへのフォールバックがないことを確認できる |
| 5. 検証完了 | テストおよび実環境検証（外部連携、認証・権限、障害耐性等）を実施・記録する | 受け入れ条件を満たし、必須修正が完了している |

- **合意済みの仕様**: 既に仕様が確定している場合は、モック作成を省略して実装へ進めます。
- **合意の基準**: 動作する状態を提示して合意を形成します。未合意の仕様に依存する実装は行わず、先行可能な調査等を進めます。
- **技術検証の先行**: 外部連携や権限等の実現性が仕様判断に直結する場合は、最小限の実接続検証を先行できます。
- **仕様変更**: 合意済みの内容を変更する場合は、理由と影響を提示して再合意します。

<a id="boundaries"></a>
## 3. モックを作り込みすぎない

- 合意に必要な表示・状態遷移のみを再現し、業務ロジックや永続化処理をモック側に再実装しない。
- 本番用と別系統の画面や専用通信層を作らず、固定データや既存の仕組みを活用する。
- モックデータは本番の型・契約に合わせて管理し、検証には既存の型検査等を用いる。
- 新規モックツールを採用する場合は、導入理由と保守負担を評価してプロジェクト定義に記録する。
- 本番構成ではモックを無効化し、実処理エラー時のモックへのフォールバックは行わない。

## 4. 記録と実装への引き継ぎ

モック専用の仕様書は新設せず、既存の正本で一元管理します。

| 正本の記載箇所 | 記録内容 |
| --- | --- |
| 機能仕様 | シナリオ、期待結果、確認対象のモックと版、合意内容（判断者・日付・根拠） |
| 設計・実行手順 | モック境界とデータの配置、起動・状態再現・終了・実処理切替手順 |
| 検証結果 | シナリオに対応する実装・テスト、対象環境と版、モック確認・実処理検証それぞれの証跡 |
| 作業計画 | 未決事項、依存範囲、進捗状態と解消条件 |

モック合意は実処理（認証・保存・性能・障害耐性等）の動作を保証しないため、実環境での検証を必須とします。不要になったモック資産は整理し、回帰テスト等に有用なもののみ保持します。
